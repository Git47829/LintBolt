Blazingly fast multithreaded HTML linter

2026-08-25 · Codex · Implemented · Approach B

Overview

This project creates a greenfield Rust command-line linter for coding agents that repeatedly generate, inspect, and repair HTML artifacts. The primary loop is one agent invoking one native binary on one recently written file or standard input, receiving compact deterministic diagnostics, and applying the next edit without waiting for a language runtime or remote service. Directory-wide continuous integration (CI) remains a secondary use case.

“Blazingly fast” becomes a competitive acceptance contract rather than a slogan. The first release includes a three-file agent-artifact benchmark against Biome, HTMLHint, HTML-Validate, Markuplint, and the Nu Html Checker; bounded-memory checks; cold-process latency; and derived multi-file scaling measurements. Done means the linter is correct on its declared HTML and rule envelope, produces the same output at every thread count, and proves a material lead over the fastest qualifying alternative on named hardware.

Measured outcome: The implementation and corpus now exist. On the recorded 8-way Apple ARM machine, the final common-rule build measured 3.45 ms, 6.87 ms, and 57.10 ms median on the three fixtures. It beat the fastest qualifying competitor on each fixture, including a 1.55× lead over Biome on 16 MiB. Raw samples and exclusions are stored in benchmarks/results/.

Goals and non-goals

Goals

  • Discover .html and .htm files while respecting .gitignore, .ignore, explicit globs, symlink policy, and a configurable maximum file size.
  • Accept a direct path or stdin plus a logical filename, with a compact JSON diagnostic format designed for agent tool calls and bounded output budgets.
  • Use a serial caller-thread fast path for one small artifact when starting or scheduling a worker pool costs more than the available parallel work.
  • Use all available cores across independent files while keeping single-file parser state isolated to one worker.
  • Report rule ID, severity, file, byte span, line, column, primary message, and optional help in deterministic path-and-offset order.
  • Expose a typed rule interface that avoids per-token heap allocation and makes rule state local to a document.
  • Emit compact JSON only. Human-oriented terminal rendering, ANSI styling, and Static Analysis Results Interchange Format (SARIF) are outside version one.
  • Target at least 750 MB/s for the lexical-rule benchmark and 250 MB/s for the full structural-rule benchmark on an eight-physical-core reference machine with a warm filesystem cache.
  • Run at least 1.5× faster than the fastest qualifying existing tool on the large-repository common-rule profile, measured end to end with pinned versions and equivalent findings.
  • Keep the small clean artifact at or below the fastest qualifying tool’s median cold-process latency, with a target P95 ≤25 ms on the named reference machine.
  • Keep the benchmark run below 256 MiB peak resident memory at eight workers, excluding the operating-system page cache.
  • Track cycles per input byte, branch-miss rate, and last-level-cache misses alongside wall time so a throughput regression can be attributed to scheduling, memory locality, or control flow.
  • Test tokenizer behavior, rule behavior, deterministic parallel output, configuration, CLI snapshots, fuzz properties, and performance regressions.

Non-goals

  • Execute JavaScript, compute CSS, fetch network resources, or reproduce a browser rendering engine.
  • Claim complete conformance checking for every requirement in the continuously maintained HTML Standard in the first release.
  • Parse framework template languages such as JSX, Vue, Handlebars, or Jinja unless a later dialect layer defines their syntax.
  • Ship autofixes, a language server, dynamic native plugins, or a daemon before the core CLI and rule contract stabilize.
  • Parallelize arbitrary byte ranges inside one HTML document; tokenizer state makes file-level parallelism the safe default.

Current state

The workspace is empty: it has no Cargo package, source files, tests, configuration, Git history, or local architecture conventions. Today an agent-created HTML artifact has no fast verification path through this project, as Figure 1 shows. This makes every public interface reversible at the design stage, but it also leaves product scope and compatibility requirements unresolved.

Constraints and dependency assumptions

  • HTML tokenization is stateful within a document. The architecture gains safe parallelism by processing documents independently instead of splitting arbitrary byte ranges.
  • html5gum provides WHATWG tokenization with exact source spans and callback/custom emitters. Approach B uses that span-aware streaming API because precise JSON diagnostics cannot be recovered reliably from html5ever's public token sink.
  • Rayon provides work-stealing parallel iterators and configurable thread pools. ignore::WalkBuilder provides parallel, Git-aware filesystem traversal.
  • The HTML Standard changes continuously. Rule documentation must identify its supported semantics and avoid implying total validator coverage.
  • The implementation targets the stable Rust toolchain available on the benchmark machine. A published minimum supported Rust version (MSRV) requires dependency re-evaluation before release.
  • Diagnostic ordering must not depend on task completion order. Workers return file-local vectors; one collector sorts and renders after all tasks finish.
  • Most agent invocations touch one small or medium artifact. Automatic scheduling must avoid filesystem walks and thread-pool work unless the input set or byte count crosses a benchmark-selected threshold.

Performance claim contract

The project earns the word “faster” through a correctness-first benchmark. Figure 2 shows the release gate; a timing result does not count when a tool produces a materially different finding set.

  • Competitors: Pin Biome, HTMLHint, HTML-Validate, Markuplint, and Nu Html Checker releases in a lock file. Measure the Nu checker both as a standalone CLI and as a prewarmed local service.
  • Primary fixtures: Version the three agent-oriented HTML files defined in the next section, including deterministic generation seeds, exact byte sizes, content hashes, and expected finding manifests.
  • Profiles: Run syntax-only, common structural rules, and each tool’s recommended/default profile separately. Only the first two profiles support head-to-head claims.
  • Correctness: Normalize findings to rule category, file, and span; require the expected common-rule findings before admitting a tool and profile to timing.
  • Timing: Use hyperfine with at least 20 measured runs. Measure cold-process agent invocations without warmups separately from warm-cache throughput runs with five warmups; randomize competitor order and export JSON evidence.
  • Scaling: Derive property-preserving multi-file sets from the three primary fixtures, then measure this project at 1, 2, 4, 8, and automatic worker counts. Require at least 70% parallel efficiency from one to eight workers on the derived large set.
  • Microarchitecture: Record cycles per byte, instructions per byte, branch misses, L1 data-cache misses, and last-level-cache misses when the platform exposes them. Treat these as diagnostic trends rather than portable absolute gates.
  • Release gate: Require no slower median latency than the fastest qualifying competitor on the small clean artifact, ≥1.25× its speed on the mixed repair artifact, ≥1.5× its throughput on the large generated artifact, and ≤256 MiB peak resident memory. If any gate fails, block the “faster for agents” claim and optimize or revisit Approach C.

Cross-tool controls

  • Generate each file from a checked-in seed and record its SHA-256 hash, byte count, element count, maximum depth, raw-text byte share, attribute distribution, and expected findings.
  • Use the intersection of semantically equivalent rules for competitive timing. Run each tool’s recommended profile separately and label it as a coverage comparison, not a speed ranking.
  • Measure direct file paths for every tool. Add a separate stdin result only where the tool supports it; never compare one tool’s stdin path with another tool’s filesystem path as the headline result.
  • Include real diagnostic emission in the mixed-repair timing. Validate normalized output outside the timed region, and disable diagnostic caps so every tool processes all 256 expected findings.
  • Measure the Nu checker’s cold CLI and prewarmed service as distinct products. Keep service startup outside warm-service timing and label the result accordingly.
  • Randomize tool order, keep the filesystem page-cache policy identical, document CPU frequency and power settings, and publish raw hyperfine JSON rather than only relative bars.

Derived multicore sets

Three single files measure the dominant agent loop but cannot prove multithreaded scheduling. Generate path-distinct, seed-varied derivatives with the same structural properties: many small clean artifacts to stress dispatch, medium repair artifacts to stress worker-local diagnostics, and enough large reports to reach at least 512 MiB total input. Measure those sets separately at fixed worker counts; do not mix their scaling numbers into the three single-file headline.

Cache affinity, cache lines, and branch prediction

The hot path must minimize cross-core ownership changes and unpredictable control flow. These choices remain benchmark-driven because cache geometry, simultaneous multithreading, operating-system scheduling, and branch predictors vary by processor.

Optimization rule: Prefer ownership and layout changes that remove shared writes or copied data. Add affinity controls, cache-line padding, profile-guided optimization, or architecture-specific code only when a reproducible benchmark identifies that mechanism as the bottleneck.

Approach A: Build a DOM per worker

Favor rule expressiveness and browser-like tree semantics with conventional file-level parallelism.

The dispatcher assigns each file to a Rayon worker. The worker parses a complete DOM with html5ever, then runs rule visitors over the tree. Rules can inspect ancestors, siblings, implied elements, and document-wide indexes without inventing a second structural model. Figure 3 traces this five-stage path.

What changes

  • Components: Create a CLI, configuration loader, ignore-aware discovery layer, Rayon dispatcher, html5ever tree adapter, rule registry, DOM visitor API, diagnostic model, renderers, and benchmark harness.
  • Data model: Keep one owned DOM plus per-document indexes for IDs and rule metadata in each active worker.
  • Interfaces: Rules implement document and node callbacks such as check_document and check_element; a typed RuleContext collects findings.
  • Dependencies: Use html5ever with a DOM implementation, rayon, ignore, clap, serde, a TOML parser, and terminal diagnostic support.

Cost and consequences

Budget about 3–4 engineering weeks, 3,500–4,500 production lines across 16–20 source files, and 20–30 focused tests plus conformance fixtures. The design makes new structural rules inexpensive, but it commits every file to full-tree allocation before the first result. Pointer-rich nodes enlarge the worker working set and add less-predictable traversals after parsing. Later streaming optimization requires either a second rule API or a rewrite of rules that depend on tree traversal.

Approach B: Fuse tokenization and rules

Stream standards-aware tokens through allocation-conscious rules while parallelizing independent files.

A direct path or stdin invocation parses one small artifact on the caller thread, avoiding filesystem discovery and worker-pool scheduling. Larger input sets feed html5gum's span-aware tokenizer to bounded workers through an adaptive dispatcher. Rules consume start tags, end tags, text runs, comments, doctypes, and parse errors while each execution context maintains compact facts: the open-element stack, head metadata, ID definitions and references, and source line indexes. Worker-owned scratch buffers and diagnostics preserve cache locality, while event-kind rule buckets keep disabled or irrelevant rules out of the branch-heavy token loop. The linter never builds a general-purpose DOM. Figure 4 shows the parallel path.

What changes

  • Components: Create the same CLI, configuration, discovery, scheduling, diagnostics, renderers, and benchmark layers as Approach A, plus direct-path and stdin adapters, an adaptive serial/parallel threshold, a streaming event adapter, compact document facts, and rule phase declarations.
  • Data model: Keep borrowed or interned token data for the duration of a callback, a small open-element stack, line-start offsets, selected document indexes, and a file-local diagnostics vector. Split frequently accessed parsing facts from cold messages and renderer metadata.
  • Interfaces: Rules implement on_event(&Event, &mut RuleContext) and finish(&DocumentFacts, &mut RuleContext). The registry constructs fresh rule state for every file and shares immutable configuration across workers.
  • Dependencies: Use html5gum span-aware tokenizer APIs, rayon, ignore, and serde. Keep argument parsing small and emit JSON directly; avoid a DOM crate, terminal renderer, and configuration parser in the default path.

Cost and consequences

Budget about 5–7 engineering weeks, 5,000–7,000 production lines across 22–28 source files, and 35–50 focused tests plus tokenizer fixtures, property tests, cache-line stress tests, dispatch microbenchmarks, and corpus benchmarks. The rule API stays close to the hot path and keeps memory bounded. Rules that need arbitrary sibling traversal, browser-inserted nodes, or repeated subtree queries require a targeted fact index or an explicitly slower tree phase; the project cannot pretend those operations are free.

Approach C: Add a SIMD fast path with parser fallback

Optimize machine-generated, regular HTML with a custom scanner and preserve a standards-aware escape hatch.

A custom byte scanner uses memchr-style vectorized searches to find candidate tag and attribute boundaries over buffered or memory-mapped input. Fast-path rules execute directly on byte spans. Documents containing raw-text states, malformed constructs, unusual encodings, or other unsupported patterns route to html5ever so the CLI returns a result instead of failing open. Figure 5 makes the two parsing paths explicit.

What changes

  • Components: Create the shared CLI and orchestration layers plus a custom byte scanner, fast-path eligibility detector, borrowed-span rule API, fallback adapter, differential test harness, and fallback telemetry.
  • Data model: Keep byte spans into worker-owned input, compact scanner state, fast-path document facts, and a common diagnostic representation shared with the fallback parser.
  • Interfaces: Fast rules consume normalized byte-span events; fallback rules consume equivalent events translated from html5ever. Every rule declares whether both paths preserve its semantics.
  • Dependencies: Add memchr and optionally memmap2 to the shared dependencies, while retaining html5ever as the compatibility path.

Cost and consequences

Budget about 8–12 engineering weeks, 8,000–12,000 production lines across 30–40 source files, and 70–100 tests including fuzzing and differential comparison against html5ever. The vectorized delimiter scan improves the regular fast path, but eligibility checks and fallback transitions add branches and instruction-cache pressure. The design creates a credible path beyond parser-bound throughput for regular generated HTML. It also commits the project to maintaining two observable parsing paths, documenting fallback coverage, and auditing any memory-mapped input because concurrent file mutation can invalidate safety assumptions.

Recommendation

Approved: Build Approach B with html5gum's span-aware stream, compact JSON-only output, and the three-file competitor benchmark.

Five factors decide the recommendation. First, a native caller-thread stream path minimizes the dominant one-artifact agent loop. Second, file-level work stealing remains available when an agent or CI supplies enough independent work. Third, html5gum's exact source spans and callback/custom emitters let the implementation fuse parsing and rule evaluation without reconstructing diagnostic locations. Fourth, compact worker-owned facts avoid shared writable cache lines and keep the active working set small. Fifth, event-kind rule buckets and cold recovery paths reduce unpredictable branches without introducing a second parser.

Implement the architecture in benchmark-gated slices: add direct path/stdin execution and deterministic compact JSON diagnostics, the tokenizer adapter and common lexical rule profile, adaptive dispatch, the three deterministic agent fixtures, competitor adapters, raw benchmark evidence, and then performance hardening driven by measured results.

The case against

Approach B makes complex tree-oriented rules harder to express than Approach A. A rule that asks repeated arbitrary ancestor, sibling, or implied-node questions can turn compact facts into a shadow DOM. That objection does not win for the proposed first release because the product has not yet committed to a DOM-heavy compatibility rule set, and the architecture can add a clearly marked opt-in tree slow lane after benchmarks show its cost.

What would change this

Choose Approach A if the selected rule catalog shows that more than 20% of enabled rules require arbitrary tree navigation or browser-inserted nodes. Move from Approach B to Approach C if the Phase 0 prototype cannot reach a 1.5× lead over the fastest qualifying competitor after profiling, at least 90% of production input qualifies for the fast path, and the team accepts an additional 8–12 weeks of parser and fuzzing work.

Open questions

  1. Which rule contract defines version one: a new curated set, compatibility with an existing linter, accessibility checks, HTML conformance checks, or a named combination?
  2. Which outputs are mandatory at launch? Resolved: compact JSON only.
  3. What corpus and machine define “blazingly fast,” including file count, total bytes, median file size, largest file, storage type, core count, and warm-versus-cold cache?
  4. Which platforms and minimum Rust version must release binaries support?
  5. Should version one reject template syntax, ignore template regions, or support named dialect adapters?
  6. Does CI require fail-fast behavior, a maximum diagnostics count, warning thresholds, and stable exit codes beyond success, findings, and operational failure?
  7. Should Biome, HTMLHint, HTML-Validate, Markuplint, and both Nu checker modes remain the mandatory competitor set, or do you need compatibility with another named tool?
  8. Is a one-shot CLI with stdin sufficient for your agents, or should a later phase add a persistent JSON-lines server to amortize process startup across many artifact checks?
